# Project Status Report

`ProjectStatusReport` — переносимый LLM-скилл для подготовки **Отчета о состоянии проекта (ОСП)** по проектной документации и переписке.

Скилл собирает данные из проектного контекста, выгруженных переписок, договора, всех применимых дополнительных соглашений, актов, предыдущего ОСП и других проектных материалов, проверяет данные на противоречия, рассчитывает процент выполнения работ и формирует **четырехстраничный DOCX**:

1. **Общие сведения** — паспорт проекта, сводные данные, план и статус этапов / ДС, общий статус, план / факт оплат.
2. **Данные по задачам** — договорные задачи и отдельный блок оперативных фактов.
3. **Риски проекта**.
4. **Ключевые вопросы и проблемы** — контроль состояния проекта и открытые действия.

Главный принцип: **не придумывать отсутствующие данные**. Источники и степень подтверждения сохраняются во внутренней модели и working-версии, а clean ОСП остается понятным Заказчику и не содержит служебных формулировок.

## Основные правила v0.6.0

### Первая страница

Паспорт проекта выводится вертикально: **одна сущность = одна строка**.

Обязательные поля:
- Заказчик;
- Проект;
- Руководитель проекта от Исполнителя;
- Руководитель проекта от Заказчика;
- Основание: договор + все применимые ДС;
- Номер отчета;
- Отчетный период.

Отдельно формируется блок **«Сводные данные по проекту»**:
- дата начала проекта;
- текущий этап;
- утвержденный бюджет;
- расчетное освоение и общий процент выполнения.

Далее формируется таблица **«План и статус этапов / дополнительных соглашений»**. Для каждого применимого этапа / ДС показываются:
- план начала;
- факт начала;
- отклонение по началу;
- план завершения;
- факт завершения;
- отклонение по завершению;
- статус;
- бюджет;
- освоено / процент выполнения.

Если по проекту несколько ДС, учитываются все применимые ДС и связанные с ними этапы, сроки, бюджеты и оплаты.

### Статусная модель работ

В clean ОСП используются только четыре видимых статуса:

| Статус | Коэффициент |
|---|---:|
| Выполнено | 100% |
| На согласовании | 90% |
| В работе | 50% |
| Не начато | 0% |

Входные формулировки `Согласовано`, `Принято`, `На приемке`, `На проверке`, `Факт не подтвержден` и другие синонимы нормализуются runtime в одну из четырех стандартных строк.

Платежные статусы — отдельная модель и не смешиваются со статусами работ.

### Оперативные задачи

Оперативные задачи:
- хранятся в `operational_items`;
- отображаются отдельным блоком на странице 2;
- не участвуют в расчете прогресса;
- не заменяют договорный baseline.

### Контроль состояния проекта

На странице 4 используется название **«Контроль состояния проекта»**. Формулировка `Health check` в клиентском ОСП не используется.

## Архитектура

```text
Контекст проекта / чат / договор / ДС / предыдущий ОСП
                         ↓
                LLM extraction pass
                         ↓
       external project state:
       report-data.json + sources.json
                         ↓
       deterministic validation + calculations
                         ↓
              working.docx + clean.docx
```

LLM отвечает за извлечение смысла и сопоставление источников. Формулы прогресса, нормализация статусов, проверки бюджетов, consistency checks и рендеринг выполняются детерминированно.

```text

- отдельно покажи план / факт оплат.

Не начато / В работе / На согласовании / Выполнено.
Другие входные формулировки нормализуй в эти четыре статуса.
Платежные статусы не смешивай со статусами работ.

Рассчитай прогресс по стоимости договорных работ.
Не допускай двойного учета родительских и дочерних строк.
Оперативные задачи показывай отдельным блоком на странице 2 и не включай их
стоимость в расчет прогресса.

На странице 4 используй название «Контроль состояния проекта»,
а не «Health check».

Сформируй:
1. clean DOCX для отправки Заказчику;
2. working DOCX с комментариями-источниками;
```

## Приоритет источников

1. Подписанный договор / ДС / акт / УПД / официальное подтверждение платежа.
2. Более поздний официальный документ того же уровня.
3. Предыдущий утвержденный ОСП — для continuity.
4. Протокол встречи / task tracker / Confluence / Bitrix24.
5. Выгруженная проектная переписка.
6. Текущий проектный чат — только как рабочий источник.

## Расчет прогресса

Расчет ведется **по стоимости**, а не по количеству задач.

```text
освоенная стоимость = бюджет строки × коэффициент статуса
процент выполнения = Σ освоенной стоимости / общий бюджет × 100%
```

Не допускается двойной учет родительских и дочерних строк.
`operational_items` никогда не входят в расчет прогресса.

## План / факт оплат

План всегда берется из подписанного договора или ДС.

Факт классифицируется как:
- `official`;
- `project_confirmed`;
- `provisional`;
- `missing`.

В clean ОСП используются платежные статусы:
- `Оплачен`;
- `Подтвержден`;
- `Не оплачен`;
- `Требует подтверждения`;
- `Не наступил срок`.

Дата оплаты не придумывается.

## Working и clean

По умолчанию скилл создает:
- `*_working.docx` — с Word-комментариями и источниками;
- `*_clean.docx` — без служебных комментариев, для Заказчика.

Clean DOCX использует реальные Word Heading styles, обычные paragraphs и простые
`Table Grid` таблицы без shapes, nested tables, одноклеточных callouts и цветовой
семантики. Это позволяет штатно импортировать документ в Confluence.

## Локальный запуск для разработчиков

```bash
python -m pip install -r requirements.txt
python -m unittest discover -s tests
python -m project_status_report.cli examples/sample-report-data.json --out output --state-dir "../ProjectStatusReport-State/demo-project"
```

## Как уменьшить расход токенов

- сохраняйте `report-data.json`, `sources.json` и `source-manifest.json`;
- анализируйте только новые / измененные документы;
- не перечитывайте неизменившиеся договоры, ДС и архивы чата без необходимости;
- используйте предыдущий clean DOCX как ориентир;
- не просите LLM заново воспроизводить разметку: документ строит deterministic renderer.

## Confluence

Интеграция с Confluence необязательна и используется только по явному запросу.
Если исправляется уже существующий ОСП, обновляется указанная страница, а не создается дубликат.

Репозиторий не должен содержать реальные договоры, переписки и ОСП конкретных заказчиков.
