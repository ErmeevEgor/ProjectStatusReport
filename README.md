# Project Status Report

`ProjectStatusReport` — переносимый LLM-скилл для подготовки **Отчета о состоянии проекта (ОСП)** по проектной документации и переписке.

Скилл собирает данные из проектного контекста, выгруженных переписок, договора, всех применимых дополнительных соглашений, актов, предыдущего ОСП и других проектных материалов, проверяет данные на противоречия, рассчитывает процент выполнения работ и формирует либо **нативный Confluence Storage Format** (если приложен Storage Format предыдущего ОСП), либо **четырехстраничный DOCX** (если Storage Format не приложен):

1. **Общие сведения** — паспорт проекта, сводные данные, план и статус этапов / ДС, общий статус, план / факт оплат.
2. **Данные по задачам** — договорные задачи и отдельный блок оперативных фактов.
3. **Риски проекта**.
4. **Ключевые вопросы и проблемы** — контроль состояния проекта и открытые действия.

Главный принцип: **не придумывать отсутствующие данные**. План берется из договора и применимых ДС, факт — из актуальных проектных материалов.

## Основные правила v0.8.0

### Conditional output: Confluence Storage Format или DOCX

- приложен Storage Format предыдущего ОСП -> `confluence_storage`, основной выход `confluence-storage.xml`;
- Storage Format не приложен -> текущий DOCX workflow без изменений;
- оба формата явно запрошены -> оба рендера из одного `report-data.json`.

Storage Format используется как нативный structural template: даты выводятся через `<time datetime="YYYY-MM-DD" />`, Handy Status переиспользуют только существующие numeric `id` из предыдущего template, а текстовый параметр Handy `Status` не считается authoritative.

### Previous-first: предыдущий ОСП — основной шаблон

Если по проекту существует предыдущий ОСП, новый отчет **не проектируется заново**.

Предыдущий ОСП используется одновременно:
- как источник номера следующего отчета и отчетного периода;
- для незакрытых рисков, открытых вопросов и незавершенных задач;
- как **структурный шаблон** следующего ОСП.

При наличии предыдущего clean DOCX сохраняются, насколько это совместимо с обязательными правилами скилла:
- порядок страниц и разделов;
- названия разделов;
- структура таблиц;
- состав и порядок колонок;
- группировка строк;
- ширины колонок и общая визуальная иерархия.

В новом отчете обновляются данные, статусы, факты, сроки, риски, оплаты и расчет прогресса. Структура меняется только если изменился договорный объем, пользователь явно просит новую структуру или прежняя структура конфликтует с обязательным правилом скилла.

Если предыдущего ОСП нет, используется встроенный fallback-шаблон из `portable-skills/project-status-report/references/report-structure.md`.

> Важно: previous-first — правило LLM/document orchestration. Standalone CLI, получивший только `report-data.json`, использует встроенный fallback renderer; предыдущий DOCX должен быть передан в рабочий контекст LLM как структурный шаблон.

### Страница 2 — стабильная таблица задач

Если предыдущий ОСП есть — структура таблицы `Данные по задачам` переносится из него.

Fallback-структура для первого ОСП:

| Код задачи | Наименование | Задача | Статус | Бюджет | Освоено | План начала | План завершения | Факт | Комментарий |
|---|---|---|---|---:|---:|---|---|---|---|

Правила:
- `Код задачи` — код ФР / договорной строки, а не порядковый номер;
- `Наименование` — человекочитаемое название требования / работы;
- `Задача` — конкретный договорный подэтап или результат;
- `План начала` и `План завершения` — отдельные колонки;
- `Наименование` и `Задача` не склеиваются, если оба значения доступны.

### Первая страница

Fallback-паспорт проекта выводится вертикально: **одна сущность = одна строка**.

Обязательные данные:
- Заказчик;
- Проект;
- Руководитель проекта от Исполнителя;
- Руководитель проекта от Заказчика;
- Основание: договор + все применимые ДС;
- Номер отчета;
- Отчетный период;
- дата начала всего проекта;
- текущий этап;
- бюджет, освоение и процент выполнения;
- план / факт начала и завершения по этапам / ДС;
- общий статус проекта;
- план / факт оплат.

### Статусная модель работ

В clean ОСП используются только четыре видимых статуса:

| Статус | Коэффициент |
|---|---:|
| Выполнено | 100% |
| На согласовании | 90% |
| В работе | 50% |
| Не начато | 0% |

Платежные статусы — отдельная модель и не смешиваются со статусами работ.

### Оперативные задачи

Оперативные задачи:
- хранятся в `operational_items`;
- отображаются отдельным блоком на странице 2;
- не участвуют в расчете прогресса;
- не заменяют договорный baseline.

### Контроль состояния проекта

На странице 4 используется название **«Контроль состояния проекта»**. Формулировка `Health check` в клиентском ОСП не используется.

## Архитектура

```text
Предыдущий ОСП ───────────────┐
                             ├─> structural continuity plan
Контекст / договор / ДС ─────┤
Чаты / акты / tracker ───────┘
                  ↓
          LLM extraction pass
                  ↓
      external project state:
 report-data.json + sources.json
      + source-manifest.json
                  ↓
 deterministic validation/calculation
                  ↓
 conditional output:
   confluence-storage.xml OR
   working.docx + clean.docx
```

LLM отвечает за извлечение смысла, continuity и сопоставление источников. Формулы прогресса, нормализация статусов, проверки бюджетов и consistency checks выполняются детерминированно. Fallback DOCX рендерится runtime; при наличии предыдущего ОСП его совместимая структура имеет приоритет.

## Приоритет источников

1. Подписанный договор / ДС / акт / УПД / официальное подтверждение платежа.
2. Более поздний официальный документ того же уровня.
3. Предыдущий утвержденный ОСП — для continuity и структуры.
4. Протокол встречи / task tracker / Confluence / Bitrix24.
5. Выгруженная проектная переписка.
6. Текущий проектный чат — рабочий источник.

## Расчет прогресса

```text
освоенная стоимость = бюджет строки × коэффициент статуса
процент выполнения = Σ освоенной стоимости / общий бюджет × 100%
```

Не допускается двойной учет родительских и дочерних строк. `operational_items` никогда не входят в расчет прогресса.

## План / факт оплат

План всегда берется из подписанного договора или ДС. Факт классифицируется как `official`, `project_confirmed`, `provisional`, `missing`. Дата оплаты не придумывается.

## Working и clean

- `*_working.docx` — с Word-комментариями и источниками;
- `*_clean.docx` — клиентская версия без служебных комментариев;
- `confluence-storage.xml` — альтернативный основной выход, когда приложен Storage Format предыдущей страницы.

Clean DOCX должен быть Confluence-safe: реальные Word Heading styles, обычные paragraphs, простые `Table Grid`, без shapes/nested tables и зависимости от цветовой семантики.

## Как уменьшить расход токенов

- сохраняйте `report-data.json`, `sources.json`, `source-manifest.json` и предыдущий clean DOCX;
- анализируйте только новые / измененные документы;
- не перечитывайте неизменившиеся договоры и архивы чата без необходимости;
- не проектируйте layout заново при наличии предыдущего ОСП.

## Confluence

Интеграция с Если приложен Storage Format предыдущего ОСП, скилл формирует новый Storage Format файл для ручной вставки через Source Editor. Автоматическая публикация в Confluence выполняется только по отдельному запросу и при наличии авторизованного connector/API.
