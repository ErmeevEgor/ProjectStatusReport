# Project Status Report

`ProjectStatusReport` — переносимый LLM-скилл для подготовки **Отчета о состоянии проекта (ОСП)** по проектной документации и переписке.

Скилл собирает данные из контекста проектного чата, выгруженных переписок, договора, дополнительных соглашений, актов, предыдущего ОСП и других проектных материалов, проверяет их на противоречия, рассчитывает процент выполнения работ и формирует **четырехстраничный DOCX**:

1. Общие сведения, статус этапов, бюджет и план/факт оплат.
2. Договорные задачи и отдельный блок оперативных фактов.
3. Риски проекта.
4. Ключевые вопросы, проблемы и открытые действия.

Главный принцип: **не придумывать отсутствующие данные**. Если факт нельзя подтвердить, он не подменяется предположением: в рабочей модели он помечается как требующий подтверждения, а в чистом ОСП выводится нейтральное значение без служебного текста.

## Для чего нужен скилл

ОСП часто собирается из нескольких разнородных источников:

- договор и дополнительные соглашения задают рамки, бюджет, сроки и план оплат;
- предыдущий ОСП задает непрерывность статусов, рисков и открытых вопросов;
- проектный чат и выгруженная переписка содержат текущие факты, решения и договоренности;
- акты / УПД подтверждают завершение этапа;
- учетная система / банк подтверждают факт поступления оплат;
- task tracker / Confluence / Bitrix24 содержат фактические статусы задач и артефактов.

Скилл сводит эти источники в единую модель и отделяет **договорный baseline**, **оперативный факт**, **внутренний backlog**, **риски/отклонения** и **открытые действия**.

Страница 2 всегда строится из договорного состава работ: договор или последнее
применимое подписанное ДС определяет строки, бюджет и плановые сроки. Task tracker
только уточняет статус, факт и комментарий; его внутренние задачи хранятся в
`operational_items`, выводятся отдельной таблицей на странице 2 и не участвуют в
расчете прогресса.

## Архитектура

```text
Контекст проекта / чат / договор / ДС / предыдущий ОСП
                         ↓
                LLM extraction pass
                         ↓
       external project state: report-data.json
                 + sources.json
                         ↓
       deterministic validation + calculations
                         ↓
              working.docx + clean.docx
```

LLM отвечает за извлечение смысла и сопоставление источников. Формулы прогресса, проверки бюджетов и рендеринг документа выполняются детерминированно.

## Работа через LLM — без команд и терминала

Пользователь не должен самостоятельно запускать Python, Git, терминал или генератор. Все технические действия выполняет LLM-агент.

### Первое подключение скилла

Отправьте в Codex, Claude Code, OpenCode или другой coding-agent:

```text
Скачай репозиторий https://github.com/ErmeevEgor/ProjectStatusReport в текущую рабочую папку.

Найди скилл portable-skills/project-status-report и полностью прочитай SKILL.md.
Reference-файлы открывай только для фактически используемых режимов и источников,
не загружай весь справочник. Используй этот скилл для подготовки Отчетов о
состоянии проекта.

Проверь Python runtime и зависимости самостоятельно. Все операции с файлами, терминалом, установкой зависимостей, валидацией и генерацией DOCX выполняй сам. Не проси меня вводить команды.

После проверки сообщи, что скилл готов и какие входные источники он ожидает.
```

### Типовой запрос на формирование ОСП

Приложите новые или изменившиеся материалы проекта и отправьте:

```text
Используй скилл project-status-report из репозитория ProjectStatusReport.

Сформируй актуальный Отчет о состоянии проекта. Текущие этапы: <перечень
активных этапов>. Старые закрытые этапы в baseline и расчет прогресса не включай.

Сначала загрузи состояние проекта из <папка состояния вне репозитория>. Сравни
хэши источников по source-manifest.json и анализируй только новые или измененные
файлы и сообщения. Не перечитывай неизменившиеся договоры, ДС и архивы чата без
необходимости. Если сохраненного состояния нет, создай его.

Используй приложенные договоры/ДС, новый экспорт переписки, акты и платежные
сведения. Предыдущий ОСП используй для continuity, если он приложен или уже есть
в состоянии. Запрашивай его только если без него нельзя определить номер отчета
или незакрытые вопросы.

Не придумывай отсутствующие факты. План по срокам, бюджету и оплатам бери из договора/ДС. Факт бери из подтвержденных проектных материалов. Если факт есть только в переписке и требует официального подтверждения — отрази это во внутреннем источнике, но не пиши служебную формулировку в основном тексте ОСП.

Рассчитай процент выполнения работ по стоимости задач:
- выполнено / согласовано / принято — 100%;
- на согласовании / на приемке — 90%;
- в работе — 50%;
- не начато — 0%.

Не допускай двойного учета родительских и дочерних задач.

Сформируй clean DOCX для отправки и working DOCX с комментариями-источниками.
Обнови report-data.json, sources.json и source-manifest.json во внешней папке
состояния; не добавляй их в Git.

Confluence используй только если я отдельно попросил. Если прошу опубликовать
исправление уже созданного отчета, обнови указанную страницу, а не создавай дубль.

Перед выдачей проверь, что ОСП состоит ровно из 4 страниц и таблицы не выходят за границы листа.
```

## Что именно делает LLM

LLM должен:

1. Сначала определить текущие этапы из прямого запроса пользователя и загрузить
   внешнее состояние проекта. Предыдущий ОСП запрашивать только когда без него
   нельзя восстановить номер или continuity.
2. Прочитать договор и ДС и выделить:
   - стороны;
   - название этапа;
   - границы работ;
   - плановые сроки;
   - стоимость;
   - график и условия оплат;
   - договорные результаты.
3. Прочитать предыдущий ОСП и перенести:
   - номер отчета;
   - незакрытые риски;
   - открытые вопросы;
   - незавершенные задачи;
   - ранее зафиксированные отклонения.
4. Сравнить хэши источников и проанализировать только новый фрагмент проектного
   контекста и переписки в хронологическом порядке.
5. Сопоставить факты с более авторитетными документами.
6. Выполнить Risk Coverage Pass: проверить просроченные договорные задачи, блокеры,
   material open items, технические проблемы и continuity рисков предыдущего ОСП.
7. Сформировать `report-data.json` со ссылками на источники.
8. Запустить валидатор и устранить только ошибки модели данных, не меняя факты.
9. Сгенерировать DOCX и визуально проверить все 4 страницы.

## Приоритет источников

При конфликте источников используется следующий порядок:

1. Подписанный договор / ДС / акт / УПД / официальное подтверждение платежа.
2. Более поздний официальный документ того же уровня.
3. Предыдущий утвержденный ОСП — для непрерывности статусов.
4. Протокол встречи / task tracker / Confluence / Bitrix24.
5. Выгруженная проектная переписка.
6. Текущий проектный чат / память LLM — только как рабочий источник.

Подробные правила: [`source-priority.md`](portable-skills/project-status-report/references/source-priority.md).

## Процент выполнения работ

Расчет ведется **по стоимости**, а не по количеству задач.

Для каждой расчетной строки:

```text
освоенная стоимость = бюджет строки × коэффициент статуса
```

Итог:

```text
процент выполнения = Σ освоенной стоимости / общий бюджет × 100%
```

Коэффициенты по умолчанию:

| Статус | Коэффициент |
|---|---:|
| Выполнено / Согласовано / Принято | 100% |
| На согласовании / На приемке | 90% |
| В работе | 50% |
| Не начато | 0% |

Если стоимость указана только на договорном уровне этапов, расчет идет по этапам.
Если стоимость явно распределена по договорным дочерним задачам и полностью
покрывает утвержденный бюджет, расчет идет по ним. Родитель и дочерние строки
одновременно не учитываются. Совпадение суммы operational tracker с бюджетом не
делает tracker расчетной базой.

## Полнота рисков

Количество рисков не фиксировано. Проверяется coverage: каждая просроченная
незавершенная договорная задача и каждый открытый вопрос `high`/`medium` должны
быть связаны с риском, проблемой или отклонением либо иметь подтвержденное
объяснение отсутствия влияния. Незакрытый риск предыдущего ОСП не может исчезнуть
без результата reconciliation.

Подробно: [`progress-calculation.md`](portable-skills/project-status-report/references/progress-calculation.md).

## План / факт оплат

**План** всегда берется из подписанного договора или ДС:

- сумма;
- событие-триггер;
- срок;
- процент;
- условия оплаты.

**Факт** берется из:

1. учетной системы / банка / официального платежного подтверждения;
2. из прямого однозначного подтверждения ответственного участника проекта как
   `project_confirmed`;
3. из неоднозначной или косвенной переписки как `provisional`;
4. при отсутствии факта — `missing`.

В основной чистой версии ОСП не должно быть фраз вроде «оплачено по контексту проекта». В ней выводится нормальный управленческий статус: `Оплачен`, `Подтвержден`, `Не оплачен`, `Требует подтверждения` или `Не наступил срок`. Дата платежа не придумывается. Источник хранится в комментариях рабочей версии и в `sources.json`.

## Внутренняя и чистая версии

По умолчанию скилл создает две версии:

- `*_working.docx` — внутренняя версия с Word-комментариями, где видно источник конкретного факта;
- `*_clean.docx` — версия без комментариев и служебных формулировок для отправки Заказчику.

Clean DOCX использует реальные Word Heading styles, обычные paragraphs и простые
`Table Grid` таблицы без shapes, nested tables, одноклеточных callouts и цветовой
семантики. Светло-серая заливка заголовков используется только как косметическое
оформление и не мешает штатному импорту в Confluence.

Это позволяет сохранить трассировку данных и не засорять официальный отчет техническим текстом.

## Локальный запуск для разработчиков

Требуется Python 3.11+.

```bash
python -m pip install -r requirements.txt
python -m unittest discover -s tests
python -m project_status_report.cli examples/sample-report-data.json --out output --state-dir "../ProjectStatusReport-State/demo-project"
```

Результат:

```text
output/
├── project-status-working.docx
└── project-status-clean.docx

../ProjectStatusReport-State/demo-project/
├── report-data.json
├── sources.json
├── source-manifest.json
└── confluence.local.json        # только если Confluence настроен
```

`--state-dir` отделяет приватное рабочее состояние от публикуемых DOCX. Каталог
состояния должен находиться вне репозитория и создаваться отдельно для каждого
проекта. Если параметр не задан, CLI сохраняет прежнее поведение для обратной
совместимости и кладет JSON рядом с DOCX.

## Как уменьшить расход токенов

- сохраняйте `report-data.json` и `sources.json` между выпусками ОСП;
- храните `source-manifest.json` и сначала сравнивайте SHA-256 источников через
  `scripts/check_sources.py`: неизменившиеся файлы не нужно снова передавать в
  контекст модели;
- на следующем цикле передавайте предыдущий JSON и только новые/изменившиеся
  материалы, а старые документы перечитывайте лишь при конфликте;
- используйте предыдущий clean DOCX как визуальный эталон, но не просите модель
  заново воспроизводить его разметку: документ собирает детерминированный renderer;
- обезличенный пример в `examples/sample-report-data.json` нужен для проверки
  модели данных, а не как обязательный вход каждого запуска.

## Confluence

Интеграция с Confluence необязательна. Клиент находит последний дочерний ОСП по
дате изменения, создает новую страницу или обновляет явно указанную существующую
страницу из проверенного clean DOCX и добавляет либо заменяет вложение.

Учетные данные не сохраняются в репозитории. На Windows их можно один раз записать
в DPAPI-зашифрованный профиль текущего пользователя во внешней папке состояния:

```text
python portable-skills/project-status-report/scripts/publish_confluence.py \
  --config ../ProjectStatusReport-State/demo-project/confluence.local.json \
  --base-url https://confluence.example.ru --user user --auth basic configure
```

Токен вводится скрыто и сохраняется только в зашифрованном виде. Также поддержаны
переменные окружения. Любая публикация дополнительно требует явного
`--confirm-publish`.

Репозиторий не должен содержать реальные договоры, переписки и ОСП конкретных заказчиков. Примеры в `examples/` обезличены. Реальные проектные данные передаются LLM только в рамках конкретного проекта.
