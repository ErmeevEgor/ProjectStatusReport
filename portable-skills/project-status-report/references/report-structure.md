# Структура ОСП

Документ всегда состоит ровно из четырех страниц A4 landscape. В clean DOCX
используются реальные стили Word `Heading 1`, `Heading 2` и при необходимости
`Heading 3`, обычный `Normal` и простые таблицы `Table Grid`.

Видимый текст черный. Цвет, shading, footer/header, shapes, text boxes, nested
tables и одноклеточные callout-таблицы не являются носителями смысла. Пояснения и
управленческие выводы оформляются обычными абзацами.

## Страница 1. Общие сведения

Сразу после Heading 1 идет паспорт 4 × 4:

| Поле | Значение | Поле | Значение |
|---|---|---|---|
| Заказчик | значение | Проект | значение |
| Руководитель проекта от Заказчика | значение | Основание | значение |
| Дополнительное соглашение | значение | Номер отчета | № значение |
| Руководитель проекта от Исполнителя | значение | Отчетный период | значение |

Отдельный подзаголовок `Паспорт проекта` не используется.

### Сводные данные и общий статус

Компактная таблица 2 × 4:

| Поле | Значение | Поле | Значение |
|---|---|---|---|
| Плановый период этапа | значение | Факт | фактический период и состояние |
| Этап проекта | значение | Расчетный прогресс | значение runtime |

### Общий статус проекта

Отдельный Heading 2 и 4–6 настоящих Word list items:

1. текущая стадия;
2. результат отчетного периода;
3. текущий или следующий блок работ;
4. состояние графика;
5. бюджет/прогресс и состояние оплат;
6. главный риск или технический вопрос.

Общий статус не помещается в таблицу сводных данных.

### План и статус этапов

Колонки:
- Этап / подэтап
- Трудоемкость
- Бюджет
- Статус
- Коэф.
- Освоение
- Комментарий

После таблицы обычный paragraph, сформированный runtime:

`Итоговый прогресс: бюджет ... ₽ | расчетное освоение ... ₽ | остаток ... ₽ | ...%`

Отдельной таблицы `ПРОГРЕСС И БЮДЖЕТ` нет.

### План / факт оплат

Колонки:
- Платеж
- Сумма
- План / основание по ДС
- Плановая дата / срок
- Факт
- Дата факта
- Статус

Источник не пишется в видимой таблице. Runtime выводит факт и статус из
`fact_evidence_level` и никогда не придумывает `actual_date`.

## Страница 2. Данные по задачам

Сразу после Heading 1 идет обычный абзац:

`Страница отражает договорный состав работ по <договор/ДС>. Операционные задачи не участвуют в расчете прогресса.`

### Договорные задачи

Страница отражает договорный состав работ текущего этапа. Название, бюджет и
плановые сроки берутся из договора или последнего применимого подписанного ДС.
Статус, фактическая дата, результат и комментарий берутся из актуальных материалов.

Использовать самый нижний стоимостной договорный уровень, полностью покрывающий
утвержденный бюджет, без двойного учета родителя и детей.

Колонки:
- №
- Задача / результат
- Ответственный
- Статус
- Бюджет
- Расчетное освоение
- Плановое начало
- Плановое завершение
- Фактическое завершение
- Комментарий

Если задача не имеет собственной стоимости, не распределять стоимость
искусственно. Однозначная дочерняя строка может наследовать период договорного
родителя с `date_basis=parent_stage_period`; основание хранится в working
comments и `sources.json`, но не в clean DOCX.

### Оперативные факты отчетного периода

Heading 2:

`Оперативные факты отчетного периода (не входят в расчет прогресса)`

Колонки:
- Оперативная задача
- Результат
- Ответственный
- Статус
- Срок / ориентир
- Комментарий

Источник — `operational_items`. Они отображаются на странице 2, но никогда не
участвуют в `calculate_progress()` и не заменяют contractual baseline, даже если
в них случайно заполнены бюджеты.

После таблицы runtime формирует обычный абзац с формулой выбранного progress basis,
например:

`Принцип расчета: 190 000 × 50% + 300 000 × 50% + 80 000 × 0% = 245 000 ₽; 245 000 / 570 000 = 43,0%.`

Готовая формула не хранится в LLM JSON.

## Страница 3. Риски проекта

Основная таблица:

- Дата
- Тип
- Отклонение / риск
- Вероятность / факт
- Влияние
- Влияние на проект
- Корректирующие мероприятия
- Результат / принятое решение
- Статус

Тип: `РИСК`, `ПРОБЛЕМА`, `ОТКЛОНЕНИЕ`.

После таблицы идут обычные абзацы, не таблицы:

- bold paragraph `Ключевой вывод по рискам`, затем `report.risk_summary` в
  1–3 предложениях: главный риск, угрожаемая веха и критичное действие;
- если поле не null, bold paragraph `Финансовое наблюдение`, затем
  `report.financial_observation`.

Чисто финансовое обстоятельство без влияния на срок/объем не превращается в
отдельный риск.

## Страница 4. Ключевые вопросы и проблемы

### Health check

Колонки:
- №
- Контрольный вопрос
- Ответ
- Комментарий

Вопросы:

1. Изменился состав и границы задач?
2. Есть отклонение от плановых сроков?
3. Есть проблемы планирования работ?
4. Есть организационные проблемы?
5. Есть технические проблемы?
6. Есть проблемы согласования / утверждения документов?
7. Есть открытые риски проекта?

Автоматические связи:
- #2 = `Да`, если есть открытое отклонение по сроку;
- #5 не может быть `Нет` при открытой технической `ПРОБЛЕМЕ`;
- #7 = `Да` при любом незакрытом риске, проблеме или отклонении;
- #3 = `Да` только при подтвержденной проблеме планирования/организации работ,
  а не из-за самого наличия риска.

### Открытые вопросы / действия

Колонки:
- Открытый вопрос / действие
- Необходимое действие / решение
- Ответственный
- Срок
- Статус / результат

Compound open items с независимыми действиями и разными состояниями разделяются
на отдельные строки.

После таблицы обычный paragraph:

`Следующий контрольный ориентир: <report.next_control_milestone>`
