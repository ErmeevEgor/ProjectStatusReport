# Структура ОСП

Документ всегда состоит ровно из четырех страниц A4 landscape.

## Страница 1. Резюме по проекту

### Паспорт
- Заказчик
- Проект
- Руководитель проекта от Заказчика
- Основание
- Дополнительное соглашение
- Номер отчета
- Руководитель проекта от Исполнителя
- Отчетный период

### Сводные данные
- Плановый период этапа
- Фактическое начало / завершение
- Этап проекта
- Общий статус проекта

"Общий статус проекта" — 4–6 управленческих тезисов:
1. где находится проект;
2. что завершено;
3. что делается / что дальше;
4. есть ли отклонение по срокам;
5. состояние оплат;
6. ключевой риск/зависимость.

### План и статус этапов

Колонки:
- Этап
- Трудоемкость
- Бюджет
- Статус
- Коэффициент статуса
- Расчетное освоение
- Комментарий

### Итоговый прогресс

Показать:
- общий бюджет;
- расчетное освоение;
- остаток;
- процент выполнения.

### План / факт оплат

Колонки:
- Платеж
- Сумма
- План / основание по ДС
- Плановая дата / срок
- Факт
- Дата факта
- Статус

Источник не пишется в видимой таблице.

## Страница 2. Данные по задачам

Страница 2 отражает договорный состав работ текущего этапа. Название, бюджет и
плановые сроки берутся из договора или последнего применимого подписанного ДС.
Статус, фактическая дата, текущий результат и комментарий берутся из актуальных
проектных материалов.

Task tracker, backlog, технические задачи, поручения и operational-декомпозиция не
заменяют договорные строки и не выводятся на страницу 2. Использовать самый нижний
стоимостной договорный уровень, полностью покрывающий утвержденный бюджет, без
двойного учета родителя и детей.

Колонки:
- №
- Задача / результат
- Ответственный
- Статус
- Бюджет
- Расчетное освоение
- Плановое начало
- Плановое завершение
- Фактическое завершение
- Комментарий

Если задача не имеет собственной стоимости, оставлять бюджет пустым; не распределять стоимость искусственно.

Если у стоимостной дочерней строки нет собственных дат, но ее связь с договорным
родительским этапом однозначна, разрешено унаследовать период родителя с
`date_basis=parent_stage_period`. При неоднозначной связи даты не наследовать.
Основание наследования хранится в JSON, комментарии рабочей версии и `sources.json`,
но не показывается в чистом DOCX.

## Страница 3. Риски проекта

Колонки:
- Дата
- Тип
- Отклонение / риск
- Вероятность / факт
- Влияние
- Влияние на проект
- Корректирующие мероприятия
- Результат / принятое решение
- Статус

Тип:
- РИСК
- ПРОБЛЕМА
- ОТКЛОНЕНИЕ

Перед заполнением таблицы выполнить checklist из
[`risk-identification.md`](risk-identification.md): просрочки договорных задач,
блокирующие зависимости, технические проблемы, material open items и continuity
незакрытых рисков предыдущего ОСП. Проверяется полнота покрытия, а не минимальное
количество рисков.

Таблица должна помещаться в ширину страницы. Использовать компактный шрифт и фиксированные ширины.

## Страница 4. Ключевые вопросы и проблемы

### Health check

Вопросы:
1. Изменился состав и границы задач?
2. Есть отклонение от плановых сроков?
3. Есть проблемы планирования работ?
4. Есть организационные проблемы?
5. Есть технические проблемы?
6. Есть проблемы согласования / утверждения документов?
7. Есть открытые риски проекта?

Ответ на п.7 выводится автоматически из страницы рисков.

Ответ на п.2 равен `Да`, если есть открытое отклонение от плановых сроков. Ответ на
п.7 равен `Да`, если есть хотя бы один незакрытый риск, проблема или отклонение.

### Открытые вопросы / действия

Колонки:
- Открытый вопрос / действие
- Необходимое действие / решение
- Ответственный
- Срок
- Статус / результат

Просроченный срок не скрывать.

Открытый вопрос отвечает на вопрос «что нужно решить или сделать?». Связанный риск
отвечает на вопрос «что произойдет с проектом, если это не закрыть?». Не копировать
один и тот же текст в обе таблицы.
