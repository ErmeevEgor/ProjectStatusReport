# Работа со скиллом Project Status Report v0.7

Пользователь прикладывает проектные материалы и пишет один запрос. LLM читает документы, анализирует контекст, рассчитывает прогресс, проверяет непротиворечивость данных и формирует ОСП.

Рабочие `report-data.json`, `sources.json` и `source-manifest.json` хранятся в отдельном каталоге проекта вне Git-репозитория.

## Главное изменение v0.7 — previous-first

Если предыдущий ОСП существует, он является **основным структурным шаблоном** следующего отчета.

Нужно сохранить его совместимую структуру:
- страницы и порядок разделов;
- названия разделов;
- таблицы;
- набор и порядок колонок;
- группировку строк;
- общую визуальную иерархию.

При этом обновляются только актуальные данные: статусы, факты, сроки, риски, оплаты, открытые вопросы и прогресс.

Структуру можно менять только когда:
- изменился применимый договорный объем;
- пользователь явно попросил изменить формат;
- предыдущая структура конфликтует с обязательным правилом текущего скилла.

Если предыдущего ОСП нет, используется fallback из `references/report-structure.md`.

## Первое подключение

```text
Скачай репозиторий https://github.com/ErmeevEgor/ProjectStatusReport в текущую рабочую папку.
Прочитай portable-skills/project-status-report/SKILL.md и необходимые reference-файлы.
Используй этот скилл для формирования ОСП.
Если есть предыдущий ОСП — используй его как структурный шаблон. Если нет — fallback-шаблон.
```

## Основной запрос

```text
Используй актуальный скилл project-status-report.

Перед формированием ОСП прочитай SKILL.md и необходимые reference-файлы.
Не используй правила по памяти, если они расходятся с текущей версией скилла.

Сформируй актуальный ОСП по текущему проекту.

Если есть предыдущий ОСП, используй его как основной шаблон структуры:
сохрани страницы, разделы, таблицы, порядок колонок и группировку строк;
обновляй данные, а не переизобретай формат.
Если предыдущего ОСП нет — используй fallback-шаблон скилла.

Сначала загрузи внешнее состояние проекта, если оно существует:
report-data.json, sources.json и source-manifest.json.
Анализируй только новые или изменившиеся материалы.

Используй договор и все применимые ДС. Старые закрытые этапы не включай в текущую расчетную базу.
План бери из договора/ДС. Факт — из актуальных проектных материалов. Не придумывай отсутствующие факты.

Предыдущий ОСП используй для номера нового отчета, отчетного периода, незакрытых рисков, открытых вопросов и незавершенных задач.

Рассчитай прогресс по стоимости договорных работ без двойного учета.
Оперативные задачи показывай отдельно и не включай в прогресс.

В clean ОСП используй только статусы:
Не начато / В работе / На согласовании / Выполнено.
Платежные статусы не смешивай со статусами работ.

Сформируй ровно 4 страницы:
1. Общие сведения;
2. Данные по задачам;
3. Риски проекта;
4. Ключевые вопросы и проблемы.

На странице 4 используй «Контроль состояния проекта».

Верни clean DOCX, working DOCX и обновленное внешнее состояние проекта.
Перед выдачей запусти валидацию и визуально проверь все 4 страницы.
```

## Если предыдущего ОСП нет

Fallback-структура страницы 2:

| Код задачи | Наименование | Задача | Статус | Бюджет | Освоено | План начала | План завершения | Факт | Комментарий |
|---|---|---|---|---:|---:|---|---|---|---|

`Код задачи` — код ФР/договорной строки. `Наименование` и `Задача` — разные смысловые поля. `План начала` и `План завершения` всегда отдельные колонки.

## Какие файлы лучше прикладывать

Минимальный набор:
- договор;
- все применимые ДС;
- актуальный экспорт проектного чата.

Желательно также:
- предыдущий clean ОСП — особенно важен с v0.7, так как задает структуру;
- прошлое внешнее состояние (`report-data.json`, `sources.json`, `source-manifest.json`);
- акт / УПД;
- выгрузка задач;
- протоколы встреч;
- подтверждение оплат.

## Источники

Приоритет:
1. подписанный договор / ДС / акт / платежный документ;
2. более поздний официальный документ;
3. предыдущий утвержденный ОСП;
4. протокол встречи / проектная система;
5. выгруженная переписка;
6. текущий проектный чат.

## Статусы работ

| Статус | Коэффициент |
|---|---:|
| Выполнено | 100% |
| На согласовании | 90% |
| В работе | 50% |
| Не начато | 0% |

## Договорные и оперативные задачи

Договорный baseline формируется из договора и применимых подписанных ДС. Tracker/backlog используются для факта и анализа, но оперативные поручения хранятся отдельно и не входят в прогресс.

## Working и clean

- `working.docx` — внутренняя версия с источниками;
- `clean.docx` — версия для Заказчика и Confluence.

## Как не анализировать проект заново

Для каждого проекта сохраняйте отдельную папку состояния:
- `report-data.json`;
- `sources.json`;
- `source-manifest.json`;
- предыдущий clean DOCX.

При следующем ОСП анализируются только новые/измененные материалы, а предыдущий ОСП задает структуру документа.

## Confluence

Confluence используется только по отдельному запросу пользователя. При исправлении опубликованного ОСП обновляется указанная страница, а не создается дубликат.
