# Работа со скиллом Project Status Report

Пользователь прикладывает проектные материалы и пишет один запрос. LLM сама читает документы, анализирует контекст, рассчитывает прогресс и формирует файлы.

## Первое подключение

```text
Скачай репозиторий https://github.com/ErmeevEgor/ProjectStatusReport в текущую рабочую папку.

Найди portable-skills/project-status-report/SKILL.md и полностью прочитай его вместе со всеми reference-файлами, на которые он ссылается.

Используй этот скилл для формирования Отчетов о состоянии проекта. Проверь Python и зависимости самостоятельно. Все операции с файлами, терминалом, валидацией и генерацией DOCX выполняй сам. Не проси меня вводить команды.
```

## Основной запрос

```text
Используй скилл project-status-report.

Сформируй актуальный ОСП по текущему проекту. Учти весь доступный контекст проектного чата, приложенный экспорт переписки, договор, дополнительные соглашения, акты, платежные сведения и предыдущий ОСП.

Если предыдущий ОСП не приложен и я явно не сообщил, что его нет — сначала запроси его. Если предыдущего ОСП нет, это отчет №1.

План по срокам, бюджету, составу работ и оплатам бери из договора/ДС. Факт бери из проектных материалов. Не придумывай отсутствующие факты и не маскируй пробелы предположениями.

Рассчитай процент выполнения по стоимости работ с коэффициентами:
- выполнено / согласовано / принято — 100%;
- на согласовании / на приемке — 90%;
- в работе — 50%;
- не начато — 0%.

Исключи двойной учет родительских и дочерних задач.

Сформируй ровно 4 страницы:
1. Резюме по проекту;
2. Данные по задачам;
3. Риски проекта;
4. Ключевые вопросы и проблемы.

В первой странице обязательно добавь план/факт оплат и процент выполненных работ.

Верни чистый DOCX для отправки, внутренний DOCX с комментариями-источниками и кратко напиши, что заполнено автоматически, а какие данные не удалось подтвердить.
```

## Если предыдущего ОСП нет

Можно сразу добавить:

```text
Предыдущего ОСП нет. Считай этот отчет первым.
```

Тогда LLM не должна спрашивать его повторно.

## Какие файлы лучше прикладывать

Минимальный набор:
- договор;
- актуальное ДС;
- экспорт проектного чата.

Желательно также:
- предыдущий ОСП;
- акт/УПД;
- выгрузка задач;
- протоколы встреч;
- подтверждение оплат.

## Как разделяются задачи и риски

Страница 2 показывает только оплачиваемый договорный baseline из договора и
актуального подписанного ДС. Tracker, backlog и технические поручения используются
для фактического статуса и анализа, но хранятся отдельно в `operational_items`, не
выводятся на страницу 2 и не участвуют в проценте выполнения.

Перед страницей 3 скилл отдельно проверяет просроченные договорные задачи,
блокирующие зависимости, технические проблемы, открытые вопросы `high`/`medium` и
незакрытые риски предыдущего ОСП. Минимального количества рисков нет: важна полнота
покрытия материального влияния на договорный результат.

## Что происходит с источниками

В основном ОСП нет технических формулировок вида «по данным чата».

Внутренняя версия содержит Word-комментарии с источником конкретных фактов. Чистая версия предназначена для отправки Заказчику и этих комментариев не содержит.

## Что делать, если источники противоречат друг другу

LLM не должна выбирать вариант наугад.

Приоритет:
1. подписанный договор / ДС / акт / платежный документ;
2. более поздний официальный документ;
3. предыдущий ОСП;
4. проектная система;
5. протокол;
6. переписка.

Если конфликт остается — поле помечается как требующее подтверждения и кратко указывается в итоговом сообщении пользователю.
