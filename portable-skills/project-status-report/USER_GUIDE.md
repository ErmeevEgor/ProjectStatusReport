# Работа со скиллом Project Status Report

Пользователь прикладывает проектные материалы и пишет один запрос. LLM читает
документы, анализирует контекст, рассчитывает прогресс, проверяет
непротиворечивость данных и формирует ОСП.

Рабочие `report-data.json`, `sources.json` и `source-manifest.json` хранятся в
отдельном каталоге проекта вне Git-репозитория.

## Первое подключение

```text
Скачай репозиторий https://github.com/ErmeevEgor/ProjectStatusReport в текущую рабочую папку.

Найди portable-skills/project-status-report/SKILL.md и полностью прочитай его.
Из reference-файлов открывай только те, которые нужны для текущего режима и источников.

Используй этот скилл для формирования Отчетов о состоянии проекта.
Проверь Python и зависимости самостоятельно.
Все операции с файлами, терминалом, валидацией и генерацией DOCX выполняй сам.
Не проси меня вводить команды.
```

## Основной запрос

```text
Используй актуальный скилл project-status-report.

Перед формированием ОСП прочитай SKILL.md и необходимые reference-файлы.
Не используй правила по памяти, если они расходятся с текущей версией скилла.

Сформируй актуальный ОСП по текущему проекту.

Текущие этапы: <указать, если известно>.
Если их можно однозначно определить из актуальных ДС — определи самостоятельно.
Старые закрытые этапы не включай в текущую расчетную базу.

Сначала загрузи внешнее состояние проекта, если оно существует:
report-data.json, sources.json и source-manifest.json.
Анализируй только новые или изменившиеся материалы.

Используй договор и все применимые ДС.
Если ДС несколько — учти каждый соответствующий этап, его сроки, бюджет и оплаты.

Предыдущий ОСП используй для номера следующего отчета, отчетного периода,
незакрытых рисков, открытых вопросов и незавершенных задач.
Если предыдущего ОСП нет — это отчет №1.
Отчетный период определяй автоматически только когда он однозначно следует
из предыдущего ОСП и даты текущего отчета.

План по срокам, бюджету, составу работ и оплатам бери из договора/ДС.
Факт бери из актуальных проектных материалов.
Не придумывай отсутствующие факты.

На первой странице обязательно должны быть:
- отдельные строки «Заказчик» и «Проект»;
- руководитель проекта от Исполнителя;
- руководитель проекта от Заказчика;
- основание: договор + все применимые ДС;
- номер отчета;
- отчетный период;
- дата начала проекта;
- блок «Сводные данные по проекту»;
- таблица по этапам / ДС с планом и фактом начала и завершения,
  отклонениями, статусом, бюджетом, освоением и процентом;
- общий статус проекта;
- план / факт оплат.

Для работ в clean ОСП используй только четыре статуса:
Не начато / В работе / На согласовании / Выполнено.
Другие входные формулировки нормализуй в эти четыре статуса.

Рассчитай прогресс по стоимости договорных работ.
Не допускай двойного учета родительских и дочерних задач.
Оперативные задачи показывай отдельно на странице 2 и не включай в прогресс.

Сформируй ровно 4 страницы:
1. Общие сведения;
2. Данные по задачам;
3. Риски проекта;
4. Ключевые вопросы и проблемы.

На странице 4 используй название «Контроль состояния проекта»,
а не «Health check».

Верни:
- clean DOCX для отправки Заказчику;
- working DOCX с комментариями-источниками;
- обновленное внешнее состояние проекта.

Clean DOCX должен корректно импортироваться в Confluence.

Перед выдачей запусти валидацию, проверь consistency между страницами,
визуально проверь все 4 страницы и убедись, что таблицы не выходят за границы.

Confluence используй только по моему отдельному запросу.
Если исправляется уже опубликованный ОСП — обновляй указанную страницу,
а не создавай дубликат.
```

## Если предыдущего ОСП нет

Добавьте к запросу:

```text
Предыдущего ОСП нет. Считай этот отчет первым.
```

## Какие файлы лучше прикладывать

Минимальный набор:
- договор;
- все применимые ДС;
- актуальный экспорт проектного чата.

Желательно также:
- предыдущий ОСП;
- акт / УПД;
- выгрузка задач;
- протоколы встреч;
- подтверждение оплат.

Если приложено несколько ДС, скилл должен определить их применимость и не
схлопывать проект в одно ДС без основания.

## Первая страница v0.6.0

### Паспорт

Каждое поле — отдельная строка:
- Заказчик;
- Проект;
- Руководитель проекта от Исполнителя;
- Руководитель проекта от Заказчика;
- Основание: договор + все применимые ДС;
- Номер отчета;
- Отчетный период.

### Сводные данные по проекту

Показываются:
- дата начала проекта;
- текущий этап;
- утвержденный бюджет;
- расчетное освоение и общий процент выполнения.

### План и статус этапов / ДС

Для каждого применимого этапа / ДС:
- план начала;
- факт начала;
- отклонение;
- план завершения;
- факт завершения;
- отклонение;
- статус;
- бюджет;
- освоено / процент.

После таблицы выводится итоговый прогресс.

Далее идут:
- общий статус проекта;
- план / факт оплат.

## Статусы работ

В clean ОСП используются только:

| Статус | Коэффициент |
|---|---:|
| Выполнено | 100% |
| На согласовании | 90% |
| В работе | 50% |
| Не начато | 0% |

Входные синонимы нормализуются в одну из четырех стандартных строк.
Платежные статусы — отдельная модель.

## Договорные и оперативные задачи

Страница 2 показывает договорный baseline из договора и применимых подписанных ДС.

Tracker, backlog и технические поручения:
- используются для фактического статуса и анализа;
- хранятся в `operational_items`;
- выводятся отдельным блоком;
- не участвуют в проценте выполнения.

## Контроль состояния проекта

На странице 4 клиентский заголовок:

`Контроль состояния проекта`

Формулировка `Health check` не используется.

## Источники

Приоритет:
1. подписанный договор / ДС / акт / платежный документ;
2. более поздний официальный документ;
3. предыдущий утвержденный ОСП;
4. протокол встречи / проектная система;
5. выгруженная переписка;
6. текущий проектный чат.

Если конфликт остается, значение не выдумывается.

## Оплаты

Для факта оплаты используются:
- `official`;
- `project_confirmed`;
- `provisional`;
- `missing`.

Clean ОСП показывает:
- `Оплачен`;
- `Подтвержден`;
- `Не оплачен`;
- `Требует подтверждения`;
- `Не наступил срок`.

## Working и clean

- `working.docx` — внутренняя версия с Word-комментариями и источниками;
- `clean.docx` — версия для Заказчика и Confluence.

Clean DOCX должен использовать стандартные Word headings, обычные paragraphs и
простые таблицы без цветовой семантики и декоративных callout-контейнеров.

## Как не анализировать проект заново

Для каждого проекта сохраняйте отдельную папку состояния:
- `report-data.json`;
- `sources.json`;
- `source-manifest.json`;
- предыдущий clean DOCX.

При следующем ОСП анализируются только добавленные / измененные материалы.

## Confluence

Confluence используется только по отдельному запросу пользователя.
Можно:
- определить последний ОСП;
- использовать его для continuity;
- создать новую страницу;
- обновить явно указанную существующую страницу;
- добавить или заменить clean DOCX во вложениях.
